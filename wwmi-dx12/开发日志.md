### 运行时管线

```
track      init_resource -> TextureTracker（候选 2D 纹理，预过滤尺寸窗口）
learn      初始数据哈希（路径 A）或 present 时 GPU 读回（路径 B，每帧限额）
match      学到的哈希 -> HashIndex 直查，或经会话缓存配对
activate   规则命中 -> 加载 mod DDS -> 上传 GPU -> 建 SRV ->
           OverrideEngine::activate -> 重写所有已记录槽位
maintain   update_descriptor_tables（create 路径）与
           copy_descriptor_tables（copy 路径，阻断+重放+改写）
           在游戏重写/复制描述符时维持替换
```

### 关键技术决策

- **ReShade Addon 而非自研 Hook**：复用 ReShade 成熟的 D3D12 拦截层（设备/命令队列/描述符/屏障事件），规避多命令表版本、设备创建路径、多线程录制等自研 Hook 复杂度。RenoDX 已验证该路线在鸣潮 DX12 下可行。
- **哈希兼容 3DMigoto**：CRC32C 数据哈希 + D3D11_TEXTURE2D_DESC CRC32C 组合，与现有 mod 生态的 `hash = xxxxxxxx` 直接互通。
- **读回时序安全**：通过 ReShade barrier 事件镜像游戏自己的资源状态转换，读回前用记录的状态做正确 barrier，避免猜测状态破坏 GPU 时间线。
- **替换纹理按文件路径缓存**：设备生命周期内复用上传副本，避免重复激活泄漏 GPU 内存。
- **own-creation 防护**：thread_local 守卫确保自建替换纹理/读回纹理不进入跟踪与哈希管线。

### 遇到的问题与修复

1. **ImGui 符号未解析（LNK2019）**
   `reshade_overlay.hpp` 仅在 `IMGUI_VERSION_NUM` 已定义时生成内联包装。`log.hpp` 先于 `imgui.h` 引入 `reshade.hpp` 导致包装被整体跳过。
   修复：`addon_main.cpp` 中 `imgui.h` 必须位于一切会拉入 `reshade.hpp` 的头之前，并加注释固化该顺序约束。

2. **ImGuiDockNodeFlags 未定义（C2061）**
   ReShade 使用 ImGui **docking 分支**，external/imgui 原为 master 分支，缺少 `ImGuiDockNodeFlags`/`ImGuiWindowClass` 等 docking 专有类型。
   修复：以 docking 分支 v1.92.5 的 `imgui.h`/`imconfig.h`/`imstb_*.h` 替换。

3. **copy 路径测试语义修正**
   `override_copy_records_dest_for_late_activation` 期望 1 次槽位改写，实际引擎正确记录了 staging 与 destination 两个槽位（2 次）。
   修复：更新测试预期，反映引擎的正确行为。

### 运行时管线（draw 拦截）

```
gate       draw_intercept 标志：无 handling=skip 规则的 mod 加载时，
           bind/draw 处理器零开销早退
bind       bind_index_buffer / bind_vertex_buffers 将 IA 绑定重放进该
           命令表的 IaState，并在此懒入池 buffer（VB/IB 角色只有 bind
           时才知道 —— ReShade 的 D3D12 后端对 buffer 统一标记 usage）
learn      present 时 GPU 读回 -> 3DMigoto 哈希公式（buffer 隐式
           COMMON 状态，无需 barrier），每帧限额（默认 1）
skip       draw / draw_indexed -> find_skip_rule：按绑定的 IB 哈希
           （indexed draw）与 VB slot0 哈希查 draw 规则；命中且
           match_* 过滤通过则返回 true，draw 不达驱动
```

### 关键技术决策

- **懒入池跟踪（bind 时准入）**：ReShade buffer 描述符不含 VB/IB 角色信息（usage flags 统一），只能在 IA bind 事件时判定角色并入池；入池时快照 byte_width，首次准入生效（后续 rebind 只刷新 LRU/计数）。
- **哈希公式对齐 3DMigoto**：`crc32c(data)` 与 `crc32c(D3D11_BUFFER_DESC{ByteWidth, Usage=DEFAULT, BindFlags=VB/IB})` 链式组合；role 进 desc 的 bind flags 区分同数据 VB/IB。与 DX11 mod 生态的 buffer hash 直接互通。
- **skip 快路径**：未入池/未学得哈希的 buffer 一律放行 draw（学习完成前不拦截），避免误杀；`draw_intercept` 原子标志让纯纹理 mod 零开销。
- **IaState 按 native 命令表句柄索引**：per-recording 快照在 destroy_command_list 时清除；槽位数取 D3D12 IA 上限 32。
- **buffer 读回无需 barrier**：D3D12 buffer 隐式 COMMON 状态，直接 copy 到 readback heap + fence 同步（复用纹理读回的 submit_and_wait）。

- `mods/Lynae-OfficeLady-WWMI-DX12/`——Lynae mod 的转换版（源件 `mods/Lynae OfficeLady(transparent) v1.1 3.5 Fix.zip`）

### 架构

```
ini_file ──> script_model ──> ScriptRuntime（每 mod 一个实例 + 独立锁）
              （if/else/endif 编译为跳转）    │
                                              ├─ 变量环境（float 语义 / persist 持久化）
                                              ├─ [Key*] cycle 按键（GetAsyncKeyState 轮询 + 边沿检测）
                                              ├─ [Resource*] 惰性 GPU 实例（.buf 上传 / ref 捕获 / copy / null）
                                              └─ GpuBridge 抽象 ──> AddonBridge（ReShade D3D12 实现）
                                                                    └─ 测试用 TraceBridge/FakeBridge
```

执行链：`draw_indexed 事件 → find_skip_rule（IB/VB0 哈希 + match_* 过滤）→ run_override(section)`
→ 执行 TextureOverride 内联脚本 → `handling = skip` 决定拦截 → 脚本内 `vb0 = ResourceX / ib = ...`
经 bridge 重绑 → `drawindexed = n, first, base` 重发替换 draw → `restore_ia` 恢复游戏原始 IA 状态。

关键设计：

- **t_script_exec 线程局部守卫**：脚本自身发出的 bind/draw 不进入 IaState 快照、不入 buffer 池、不递归拦截
- **锁序 runtime → lock**：脚本执行持 runtime 锁，bridge 调用不取全局锁
- **[Present] 脚本**在 present 事件执行（无 draw 上下文，bridge cmd=nullptr，bind/draw 自然 no-op）
- **按键轮询**在 present 事件、每帧一次；`reshade_open_overlay` 事件跟踪 overlay 可见性，overlay 打开时暂停（避免输入 overlay 文本误触按键）
- **设备销毁**时释放脚本创建的 GPU buffer 并落盘 persist 文件（`<data_root>/Persist/<mod名>.ini`）

### 踩坑记录

1. **INI 解析器丢弃无 `=` 的行**：`if x / else / endif` 整行消失。修复：ini_file 保留无值键
2. **`===`/`!==` 未词法化**：WWMI mod 大量使用三等号。按 3DMigoto 语义归一为 `==`/`!=`
3. **null 比较逻辑写反**：`ResourceX == null` 应在资源"无活实例"时为真
4. **OEM 标点 VK 码**：`,`(0xBC)/`.`(0xBE)/`/`(0xBF) 需显式映射，`VkKeyScan` 不可靠
5. **未闭合 if 块**导致 pc 越界：解析期将跳转目标钳到表尾并告警
6. **Command 含 unique_ptr 不可拷贝**：post 相位改存 `const Command*`
7. **隐式资源**：`ResourceX = ref vb0` 的 X 常无 [Resource] 定义，需 find_or_create 隐式注册

### "游戏内 ReShade 看不到插件"排查（m3-7）

ReShade 加载 addon 的必要条件，按命中率排序：

1. **ReShade 必须是带 addon 支持的版本**。reshade.me 官方安装器默认**不带** addon 支持，安装时必须勾选
   *"Enable support for third-party add-ons"*（或直接下载 "ReShade with full add-on support" 版本）。
   GShade 及各类魔改版可能永久禁用 addon。**这是最常见原因。**
2. **版本 ≥ 5.2**（addon API v5+；本项目按 API v20 头文件编译，建议 5.8+）
3. **文件位置**：`WWMI-DX12.addon64` 必须与 ReShade 的 `dxgi.dll`（或 d3d12.dll）同目录，即游戏 exe 所在目录
4. **验证方法**：打开游戏目录的 `ReShade.log`，正常应有 `Loaded add-on '...\WWMI-DX12.addon64'`；
   overlay 的 Add-ons 标签页应列出 WWMI-DX12；本插件注册了 overlay 面板，Settings → Add-ons 可见
5. 若 log 显示 "skipping add-on (not signed/failed)"，检查文件是否被杀软/反作弊隔离

鸣潮带 ACE 反作弊：ReShade 本体能运行说明注入路径已通；addon 与 ReShade 同进程同权限，一般不再单独拦截。

### 真机首测崩溃修复（2026-08-24 追加）

**现象**：进游戏约 20 秒闪退。ReShade.log 末尾：

```
[WWMI-DX12] readback compaction failed for ... (1708x964 fmt=19)   ← 半分辨率后处理 RT
[WWMI-DX12] readback map failed
ERROR Device was lost with DXGI_ERROR_DEVICE_REMOVED
ERROR > Device removal reason is DXGI_ERROR_DEVICE_HUNG.
```

**根因**：present 时刻纹理回读用了事件快照的 old_state 发 barrier。ReShade 的
`command_list::barrier` 是裸转换（不查表），游戏并行 command list 的实际状态与快照不符时
StateBefore 错误 → NVIDIA 驱动 TDR（DEVICE_HUNG）→ 闪退。且准入过滤器放行了带
shader_resource 标志的 RT（半分屏后处理目标），这类资源永远处于"使用中"状态，风险最高。

**修复**（三层防御）：

1. `is_hash_candidate` 排除 `render_target | depth_stencil | unordered_access` 用途——
   mod 目标是纯采样材质贴图，RT 内容哈希本无意义
2. 新增 `state_safe_for_readback` 门控：快照状态非"静止态"
   （SRV/copy/general 等）时跳过本轮回读，`requeue` 回 pending 并刷新 LRU tick
   （防热纹理霸占预算），下一帧重试
3. `TextureTracker::requeue`（learning→pending）与 mark_unsupported 分离，临时不安全≠永久失败

验证：构建绿灯，111 用例 / 1085 检查通过。

### 二次真机验证 + 贴图绑定修复（2026-08-24 追加）

**验证结果**：崩溃修复生效——无 DEVICE_HUNG，游戏正常运行后正常退出。
`Add-ons are still loaded!` 退出警告为 ReShade 已知行为，非阻塞。

**新发现问题**：log 中 95 条贴图规则全部报 `has no loadable texture`——贴图替换路径完全失效。

`resource` 前缀（`ResourceTexture0` → binding 存 `texture0`），但资源表 key 是

**修复**（[addon_main.cpp](../src/addon_main.cpp) `resolve_rule_textures`）：

1. 双重查找：先查剥前缀名，miss 再查 `"resource" + ref`
2. draw 拦截规则（`handling = skip/abort`）跳过贴图解析——它们走 M2/M3 draw
   管线，此前的 "no 0c33d628.dds" 告警全是误报

probe 验证：95 条贴图规则全部解析到正确 DDS，0 条 UNRESOLVED。

### 架构

```
init_pipeline ──> PipelineTracker
                  ├─ 6 阶段字节码 XXH64（vs ps gs ds hs cs，与 3DMigoto 同源）
                  ├─ subobject 缓存（blend/depth/rasterize/... 供克隆）
                  └─ LRU 淘汰（上限 4096 条，防 PSO 洪水泄漏）

bind_pipeline ──> cl_pipeline[cmd_list native] = pipeline  （draw 期查询当前 PSO）

draw_indexed ──> run_shader_overrides()
                  └─ 6 阶段哈希 → shader_overrides 索引 → run_list 段体（$attack=1 闩锁）

[Present] ──> $hb=$attack; $attack=0; $hc=$attack1; $attack1=0  （帧间闩锁）
              Component4: if $hb==1 && $hc==0 → PINGZI draw

blend 命令 ──> ScriptRuntime::_active_blend（行级合并：blend / blend_factor[N] 分开携带）
   drawindexed ──> AddonBridge::apply_blend()
                   ├─ device::clone_pipeline：缓存 subobject + 覆写 blend_desc
                   │   （未指定 blendalpha 时镜像 color；src/dst 直接透传枚举）
                   ├─ 未命中缓存按 (pipeline, cfg) 键克隆 + 引用计数复用
                   ├─ cmd_list->bind_pipeline(克隆 PSO)
                   ├─ factors 非默认 → OMSetBlendFactor（get_native 直调保 float 精度）
                   └─ 返回 token；draw 后 revoke_blend → 绑回原 PSO
```

关键设计：

- **blend 作用域 = 单次执行**：`execute()` 进入/退出各清一次 `_active_blend`，
  一次 `apply → draw → revoke` 不跨脚本泄漏；多 draw 时每次重新 apply
- **闩锁跨帧**：ShaderOverride 在帧内任意 draw 命中置位，[Present] 收集复位——
  与 3DMigoto 帧语义一致（WWMI mod 依赖此实现攻击动画窗口）
- **PSO 克隆缓存**：同 (源 PSO, blend cfg) 只克隆一次，引用计数管理生命周期，
  destroy_pipeline 时连带释放，无泄漏
- **XXH64 软实现**：无 xxHash 依赖，canonical 向量测试对齐参考实现

### 踩坑记录

1. **枚举错位**：ReShade `blend_factor` 枚举含 0/1 两个保留位（`zero`/`one`），
   3DMigoto 的 token 表是 D3D11 稠密序——`neutral ≤ 11 ? neutral : neutral + 2` 映射
2. **`to_upper` 缺失**：blend token 解析改用 `to_lower` + 小写比较表
3. **blend_constant 精度**：ReShade 的 `bind_pipeline_states` blend_constant 走
   uint32 压缩；`OMSetBlendFactor` 需全 float——用 `get_native()` 转
   `ID3D12GraphicsCommandList*` 直调
4. **blend_desc 命名空间**：subobject 里是 `reshade::api::pipeline_subobject`，
   克隆时需完整限定，否则 MSVC 解析到 D3D12 的同名类型
5. **factor_mask 合并**：多条 `blend_factor[N]` 行各自带 4bit 掩码，
   `run` 链合并时 OR 掩码、逐槽覆写（漏 OR 会让后段清掉前段的 factor）
6. **ShaderOverride 段名查找**：规则表存原始大小写（"ShaderOverrideaaa"），
   `_lists` 键是 normalize 后（"aaa"）——`run_list` 的 normalize 回退分支兜底
7. **runtime-probe 的 TraceBridge**：新增纯虚 `apply_blend/revoke_blend` 后
   probe target 编译失败（抽象类），补空实现

## M6：池化索引缓冲区域哈希——修复模型替换（已完成）

**日期**：2026-08-24
**状态**：x64 Release 构建绿灯，128 用例 / 1249 检查全部通过（较 M5 新增 3 用例）；
runtime-probe 对真实 mod.ini 回归通过；待真机部署验证

### 根因定位（来自 09:16–09:19 真机 log）

M5 的调度修复已生效（43 个 buffer 在 ~70 秒内全部哈希完成），但学到的
index buffer **全部恰好 33554432 字节（32MB）**——UE DX12 将网格索引缓冲
**池化**进共享 32MB 大缓冲，per-draw 用 `(buffer, offset)` 视图绑定。

mod 的 `0c33d628` 是 DX11 时代**专属身体 IB**（310422 索引 ≈1.2MB）的哈希
（crc32c(crc32c(data), D3D11_BUFFER_DESC{1241688,...})）。整池哈希的数据项
（32MB 混合内容）与 desc 项（ByteWidth=32MB）都与原哈希不同——**整池学习
路径在池化架构下永远不可能匹配**。`skipped_draws=0`、24 次贴图替换正常
（贴图不池化）与该结论一致。

### 方案：draw 窗口区域哈希（M6 核心）

mod 规则自带完美线索：8 个组件规则的 `(match_first_index, match_index_count)`
首尾相接（0→17970→63606→…→301470），拼接范围正是原版身体 IB 的完整索引区。
对池视图只回读 `[view_offset + min_fi*is, span)` 区域并按同一公式哈希
（desc ByteWidth = span），即可**精确复现 DX11 专属缓冲哈希**。

| 组件 | 改动 |
|---|---|
| `buffer_tracker.hpp/cpp` | 新增 `DrawWindowIndex`（按 hash 分组提取窗口，min_fi/max_end 定界）；`IndexViewTracker`（(handle,offset) 视图状态机：unverified→probing→verified/failed，失败 300 帧冷却重试，LRU≤512，verified 不可淘汰优先）；`find_skip_rule` 增加 views 参数，verified 视图优先路由 |
| `addon_main.cpp` | `load_mods` 构建 `windows`（规则移入索引前）；`evaluate_draw` 未命中且 (fi,count) 命中窗口组时入队探测（一次哈希查表+小向量扫描，draw 热路径零 GPU 开销）；`on_present` 出队执行区域回读验证（1.2MB 级，对比 32MB 整池大幅降低停顿）；设备销毁清理视图状态；detach 统计新增 M6 行 |

### 验证

### 进场景崩溃修复（10:35 真机反馈）

首版 M6 部署后：主界面正常，**进场景数秒后崩溃**。log 证据：

```
10:35:57:905 | ERROR | Device was lost with DXGI_ERROR_DEVICE_REMOVED!
10:35:57:905 | ERROR | > Device removal reason is DXGI_ERROR_DEVICE_HUNG.
```

且全程无任何 `index view` 日志——崩溃发生在首次 `verify_index_view_probe`
的 copy 内部，早于日志输出。

**根因**：区域回读**无边界校验**。span 来自 mod 窗口规则（63606×4≈254KB），
与池实际大小无关。两类场景会使 `region_offset + span` 越过提交分配区：
(1) 场景内其它 draw 的 `(first_index, index_count)` 撞上窗口签名但绑定的是
小缓冲（世界几何/UI）；(2) 正确的 32MB 池但视图靠近池尾。越界
`copy_buffer_region` → GPU fault → DEVICE_HUNG → 设备移除。主界面 draw 少、
签名不碰撞，故安全。M2 整池回读 `[0, byte_width)` 天然不越界，M5 无此问题。

**修复**（两层防线）：

1. `verify_index_view_probe`（权威）：copy 前用 `get_resource_desc` 校验
   `type==buffer && region_offset+span <= size`，越界/句柄复用则 set_failed
   并记 `index view probe out of range` 日志
2. `schedule_index_view_probe`（早期过滤）：用 bind 期记录的池大小预检，
   结构性不可满足的视图直接 set_failed 走 300 帧冷却，不送 present 线程

回归：128 用例 / 1249 检查通过；构建 640000 字节（10:45）。
新诊断日志：`index view probe out of range: buffer %p off=%llu span=%u
size=%llu`——若正确视图也报越界，说明窗口定界假设有误（需回传该行）。
